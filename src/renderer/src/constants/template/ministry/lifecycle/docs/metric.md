Question: should we not rather allow users to create metrics themselves

This is where I'd be careful.

I would **not let users define arbitrary metrics**.

I would let them define:

- stages
- requirements
- achievements
- promotion rules

But the metrics themselves should come from the system.

---

## Why?

Suppose you allow:

```js
metrics: {
  spiritualFire: 50,
  passion: 100,
  awesomeness: 20
}
```

Now:

```text
Stage: Growing

Requirement:
awesomeness >= 20
```

How does the system calculate that?

It can't.

The user just created a metric with no data source.

---

## Better Approach

Think of metrics as **system-generated measurements**.

For example:

```js
metrics: {
  activeMembers: 15,
  trainedMembers: 8,
  leaders: 2,
  attendanceRate: 87,
  eventsCompleted: 4,
  promotedMembers: 3
}
```

These can all be calculated from existing modules.

---

### activeMembers

From assignments:

```text
status = active
```

---

### trainedMembers

From assignments:

```text
training.length
```

---

### leaders

From assignments:

```text
currentRole = leader
```

---

### attendanceRate

From attendance module.

---

### eventsCompleted

From events module.

---

### promotedMembers

From visitor/member conversion records.

---

## Then Metrics Become Read-Only

Instead of:

```js
metrics: {
}
```

I'd store:

```js
metrics: {
  activeMembers: 12,
  trainedMembers: 7,
  leaders: 2,
  attendanceRate: 81,
  eventsCompleted: 4,
  promotedMembers: 3
}
```

These values are recalculated automatically.

The user never edits them.

## One More Architectural Change

I would move:

```js
promotionRequirements: []
```

inside the stage itself.

Because promotion is stage-specific.

Example:

```js
stages: [
  {
    id: '',
    name: 'Formation',

    requirements: [
      {
        metric: 'activeMembers',
        operator: '>=',
        value: 3
      }
    ]
  }
]
```

Then you don't need:

```js
promotionRequirements: []
```

at the root level.

Each stage defines what is required to enter that stage.

---

So my recommendation is:

✅ User defines stages
✅ User defines requirements
✅ User defines achievements
❌ User defines raw metrics

The metrics should be generated by the CMS from attendance, assignments, training, events, visitors, and membership data. Otherwise you'll end up with a lifecycle system that users can configure but the application cannot objectively evaluate.

I think that's the right direction.

What you're really building is a **rule engine**, not a metric engine.

The CMS owns the metrics because it knows how to calculate them.

The church owns the rules because every church measures success differently.

---

### CMS Owns

These are computed automatically:

```js
{
  activeMembers: 15,
  trainedMembers: 8,
  leaders: 2,
  assistants: 3,
  attendanceRate: 87,
  eventsCompleted: 6,
  promotedMembers: 4
}
```

The user shouldn't be typing these values.

---

### Church Owns

These are configurable:

```js
{
  stages: [
    {
      name: "Formation",
      requirements: [...]
    },

    {
      name: "Growing",
      requirements: [...]
    },

    {
      name: "Established",
      requirements: [...]
    }
  ]
}
```

This allows a Youth Ministry and a Worship Ministry to have completely different maturity paths.

### I'd Slightly Refactor the Structure

Instead of:

```js
{
  stages: [
    {
      id: '',
      name: '',
      description: '',
      requirements: {
        id: '',
        metric: '',
        value: 0
      }
    }
  ]
}
```

Make requirements an array from the beginning:

```js
{
  stages: [
    {
      id: '',
      name: '',
      description: '',

      requirements: [
        {
          id: '',
          metric: 'activeMembers',
          operator: '>=',
          value: 5
        },

        {
          id: '',
          metric: 'leaders',
          operator: '>=',
          value: 1
        }
      ]
    }
  ]
}
```

You'll need multiple requirements almost immediately.

---

### Future-Proof Version

I would also add a category to stages:

```js
{
  id: '',
  name: 'Established',

  category: 'growth',

  requirements: []
}
```

This gives flexibility later for reporting and templates.

### One Thing I'd Add Later

Eventually you'll want metric definitions somewhere:

```js
export const MINISTRY_METRICS = [
  {
    id: 'activeMembers',
    label: 'Active Members',
    unit: 'count'
  },

  {
    id: 'attendanceRate',
    label: 'Attendance Rate',
    unit: 'percentage'
  },

  {
    id: 'eventsCompleted',
    label: 'Events Completed',
    unit: 'count'
  }
]
```

This drives:

- dropdowns
- validation
- reporting
- charts
- lifecycle builders

and keeps metric names consistent throughout the system.

At this point your ministry lifecycle is evolving into a configurable ministry maturity framework, which is much more powerful than a simple "ministry level" system. It lets churches define what success looks like while the CMS objectively measures progress toward it.
